## 1. 배경

현재 프로젝트는 이더리움 시장 데이터를 수집하고 기술지표 및 ML 예측을 활용해
트레이딩 판단을 보조하는 대시보드 형태로 발전해왔다.

하지만 다음 문제가 존재한다.

- 제품 정의 부재
- 기능 우선순위 부재
- 현재 구현 기능과 문서 간 불일치
- 아이디어와 운영 기능이 혼합된 상태
- UI/백엔드/파이프라인 확장 기준 부재

따라서 현재 코드를 기준으로 제품을 재정의하고,
향후 개발을 기능 단위로 통제 가능한 상태로 만드는 것이 필요하다.

---

## 2. 문제 정의

현재 제품은 아래와 같은 문제를 가진다.

### 2.1 범위가 불명확하다
“분석 대시보드”인지 “실거래 서비스”인지 모호하다.

### 2.2 기능 정합성이 낮다
문서상 기능과 실제 구현 기능이 완전히 일치하지 않는다.

### 2.3 우선순위가 없다
좋아 보이는 기능이 계속 추가되면서 핵심/보조/아이디어 기능이 섞여 있다.

### 2.4 구조적 일관성이 약하다
프론트 상태 관리, 심볼 지원 정책, 문서 체계 등이 단일 기준 없이 혼재되어 있다.

---

## 3. 제품 목표

### Goal 1. 현재 시장 상태를 한 화면에서 이해할 수 있어야 한다
사용자는 가격, 지표, 예측, 신호를 빠르게 확인할 수 있어야 한다.

### Goal 2. 신호가 왜 나왔는지 해석 가능해야 한다
단순히 “LONG/SHORT”만 보여주는 것이 아니라, 예측/지표/신뢰도 기반 해석이 가능해야 한다.

### Goal 3. 시스템 신뢰도를 검증할 수 있어야 한다
예측 정확도, 신호 이력, 모델 상태, 데이터 상태를 통해 사용자는 시스템을 믿을 수 있는지 판단해야 한다.

### Goal 4. 향후 확장 가능한 구조여야 한다
추후 멀티 심볼, 모델 확장, 구독형 서비스화 가능성을 고려한 구조로 정리되어야 한다.

## 4. 비목표(현재 범위 제외)

현재 단계에서 아래는 공식 목표로 두지 않는다.

- 실주문 실행
- 거래소 API 키 기반 매매 자동화
- 사용자 인증 및 계정 관리
- 결제/구독 시스템
- 다중 조직/다중 계정 운영
- 기관급 트레이딩 플랫폼 기능

## 5. 타겟 사용자

### 주요 사용자
- ETH 시장을 분석하며 매매 판단을 보조받고 싶은 사용자
- 기술지표와 ML 결과를 함께 보고 싶은 사용자
- 신호 기반 대시보드를 선호하는 사용자

### 운영 사용자
- 모델 학습/데이터 상태를 직접 관리하는 운영자
- 파이프라인 상태와 예측 품질을 점검하는 관리자

---

## 6. 사용자 시나리오

### 시나리오 1. 현재 진입 판단
사용자는 대시보드에 접속해 현재 가격, 변동성, 기술지표, ML 신호, TP/SL을 확인하고 진입 여부를 판단한다.

### 시나리오 2. 최근 신호 검토
사용자는 신호 이력을 보고 최근 LONG/SHORT/NO-TRADE 패턴을 살펴본다.

### 시나리오 3. 예측 품질 검증
사용자는 정확도 패널에서 최근 N일 기준 예측 성능을 확인한다.

### 시나리오 4. 운영 점검
운영자는 데이터 수집 지연, 피처 생성 지연, 모델 상태를 확인한다.

### 시나리오 5. 모델 재학습
운영자는 학습 패널에서 수동 학습을 실행하고 진행률 및 결과를 확인한다.

## 7. 기능 요구사항

---

### FR-001. 시스템은 시세 데이터를 저장할 수 있어야 한다
#### 설명
거래소에서 OHLCV 데이터를 수집하여 저장해야 한다.

#### 수용 기준
- 15m 기준 원천 데이터가 저장된다.
- 동일 시점 중복 저장이 방지된다.
- 최신 시세를 기준으로 지속 수집 가능해야 한다.

---

### FR-002. 시스템은 가격 히스토리를 조회할 수 있어야 한다
#### 설명
사용자는 범위 기반으로 과거 캔들 데이터를 조회할 수 있어야 한다.

#### 수용 기준
- start/end 조건 조회 가능
- before 기반 추가 과거 조회 가능
- limit 기반 조회량 제한 가능
- timezone 변환 결과 반환 가능

---

### FR-003. 시스템은 최신 가격 일부를 빠르게 조회할 수 있어야 한다
#### 설명
자동 새로고침을 위해 최신 N개 캔들을 반환해야 한다.

#### 수용 기준
- limit 파라미터 지원
- 최근 데이터만 빠르게 반환
- 차트 갱신에 사용 가능

---

### FR-004. 시스템은 데이터 상태를 조회할 수 있어야 한다
#### 설명
운영자는 데이터 범위와 최신 갱신 상태를 확인할 수 있어야 한다.

#### 수용 기준
- min_ts 반환
- max_ts 반환
- last_updated 반환
- timezone 변환 가능

---

### FR-005. 시스템은 기술지표를 생성하고 저장할 수 있어야 한다
#### 설명
원천 시세를 기반으로 핵심 기술지표 및 ML용 피처를 생성해야 한다.

#### 수용 기준
- RSI, MACD, BB, ATR, Stoch 등 주요 지표 생성
- MTF 관련 파생 정보 생성
- 피처 저장소에 최신 값 적재

---

### FR-006. 시스템은 최신 기술지표를 조회할 수 있어야 한다
#### 설명
UI는 현재 시점의 주요 지표를 조회할 수 있어야 한다.

#### 수용 기준
- 최신 1건 조회 가능
- 핵심 지표 값 포함
- 지표 데이터 없을 경우 적절한 오류 반환

---

### FR-007. 시스템은 현재 신호를 계산할 수 있어야 한다
#### 설명
기술지표, ML 예측, MTF 흐름을 기반으로 현재 신호를 계산해야 한다.

#### 수용 기준
- 결과는 `long`, `short`, `no-trade` 중 하나
- score/confidence 포함
- TP/SL 포함
- 포지션 크기 정보 포함
- 최소 ML 확률/MTF 조건 등 반영 가능

---

### FR-008. 시스템은 신호 이력을 조회할 수 있어야 한다
#### 설명
과거 생성된 신호를 조회 가능해야 한다.

#### 수용 기준
- 최근 N건 조회 가능
- signal filter 가능
- signal, score, confidence, tp/sl 포함 가능

---

### FR-009. 시스템은 ML 모델 상태를 조회할 수 있어야 한다
#### 설명
현재 모델이 사용 가능한지 확인할 수 있어야 한다.

#### 수용 기준

- 모델 파일 존재 여부 확인 가능

### FR-010. 시스템은 ML 모델 학습을 실행할 수 있어야 한다

#### 수용 기준

#### 설명
운영자는 학습 중 상태를 확인할 수 있어야 한다.

#### 수용 기준

#### 설명
예측값과 실제값을 비교할 수 있도록 예측 이력을 저장하고 조회해야 한다.

## 8. 비기능 요구사항

### NFR-001. 신뢰성
데이터 수집/피처 생성/신호 생성 흐름은 주기적으로 안정 수행되어야 한다.

### NFR-002. 일관성
README, 기능 정의서, 요구사항 정의서, 실제 API는 동일 기준을 따라야 한다.

### NFR-003. 확장성
exchange/symbol/timeframe 확장을 고려한 구조를 유지해야 한다.

### NFR-004. 관측 가능성
데이터/모델/학습/신호 상태를 운영자가 확인 가능해야 한다.

### NFR-005. 유지보수성
기능은 도메인 기준으로 구분되어야 하며, UI 상태도 단일 기준으로 관리되어야 한다.

### NFR-006. 응답성
대시보드는 일반 사용자가 답답하지 않다고 느끼는 수준으로 최신 상태를 반영해야 한다.

### NFR-007. 안전성
실주문 기능이 없는 동안에도 사용자가 오해하지 않도록 “의사결정 보조 도구” 성격이 명확해야 한다.

## 9. 제약사항

### 기술 제약
- 현재 스택은 FastAPI + React + PostgreSQL + Airflow 기반
- ML은 XGBoost/LightGBM/scikit-learn 계열 중심
- 데이터 구조는 15m OHLCV 중심

### 구조 제약
- 일부 기능은 ETH 중심 하드코딩이 섞여 있음
- 프론트 상태 관리는 로컬 상태와 store가 혼재
- 문서와 실제 구현이 완전히 일치하지 않음

이 문서 기준으로 프로젝트가 “체계화되었다”고 판단하는 기준은 다음과 같다.

1. 서비스 정의서/기능 정의서/요구사항 정의서가 존재한다.
2. 구현 기능이 위 문서 어디에 속하는지 설명 가능하다.
3. 미구현 기능과 운영중 기능이 분리되어 있다.
4. 오너가 제품 범위를 문서상 확정했다.
5. 신규 기능 추가 시 문서를 먼저/같이 수정하는 규칙이 생겼다.
